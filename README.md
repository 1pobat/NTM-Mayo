# HBM Mayonnaise Addon

Независимый аддон для Minecraft 26.2 / NeoForge 26.2.0.89 / Java 25.
Mod ID: `hbmmayo`. Основной NTM NEXT не изменяется и не включается в JAR аддона.

**Статус: игровая интеграция написана, но полный Gradle build и запуск игры пока
не прошли. Устанавливаемого JAR аддона нет.** Подробности — [STATUS.md](STATUS.md).

## Целевая версия NTM NEXT

Из предоставленных частей побайтно восстановлен `ntmjar/ntm-next.jar`:

- Implementation-Version: `1.0.3+1b8c6c2d`.
- Размер: 63 534 692 байта; 6441 класс; CRC всех ZIP-записей проверены.
- SHA-256: `923a0a2bea1deded10a71cc7273cb687d728b27fe1c2ba06774150f09c28a273`.
- Mod ID: `hbm`; Minecraft `[26.2,26.3)`; NeoForge `[26.2.0.7-beta,26.3)`.
- Клиент NTM требует Crankshaft `1.6.0+mc26.2` или новее по его метаданным.

Это проверенные характеристики зависимости, **не подтверждение работоспособности
аддона**. Другие сборки NTM не заявлены совместимыми. Сборка проверяет SHA-256.

## Реализация

- Пять жидкостей через официальный `NTMFluids.register` и `FluidBuilder`.
  Native масло `hbm:sunfloweroil`, яйцо `hbm:egg`, Salient Green `hbm:salient`
  переиспользуются. Банки 250 mB и капсула 100 mB подключены через `FluidContainerRows`.
- Восемь производственных рецептов используют настоящие типы `hbm:mixer`,
  `hbm:chemical_plant`, `hbm:purex`. NTM предоставляет им свои категории JEI/REI;
  отдельная имитация машин или просмотрщика не создаётся.
- Два модуля — подклассы `ItemArmorMod` в одном нагрудном сокете `PLATE_ONLY`.
  Это обеспечивает их взаимное исключение в штатном Armor Modification Table.
- Infusion сохраняется в NeoForge attachment. DT добавляется в нативный
  `DamageResistanceHandler.getDTDR`; DR не подменяется. Скорость имеет один
  постоянный ключ transient-модификатора; исходящий урон масштабируется один раз.
- Учёт нестабильности наблюдает обычные HP внутри каждого `hurtServer` и реальные
  уменьшения через `setHealth`. Щиты и absorption не считаются обычным здоровьем.
  Вложенные удары разделяются; лечение внутри вызова не скрывает потерю HP.
- Пассивная стабилизация, Entropy Reclaimer (строго минус **7 процентных пунктов**),
  инъектор и камера имеют серверную проверку и расход энергии.
- Аннигиляция использует отдельный damage type и прямой native death, золотые
  частицы, оригинальный звук и перевод сообщения. Проверка тотема не вызывается;
  native броневое воскрешение отдельно исключается только для аннигиляции.
- Газовая турбина — найденный в этой сборке механизм со штатным баком смазки.
  Mayo допускается только в этот бак; расход остаётся нативным, выработка HE — 85%.
  При перегреве смазка превращается в Burnt Mayonnaise и перестаёт работать.
- Coolant Adapter охлаждает RBMK по геометрии и величине штатного RBMK Cooler
  с коэффициентом 0.60. Срок — 600 тиков фактической работы. Дозаправка, сохранение
  и перенос блока не омолаживают содержимое. После пригорания требуется полный слив;
  близлежащие control rods получают native `setTarget(0)`.
- HUD и его цвет — клиентские; данные отправляются только владельцу.

**Согласованное исключение:** фиксированные 125 HE/t для Mixer отменены пользователем.
Mixer использует свой штатный расход (50 HE/t без улучшений в проверенной сборке).
Ни mixin, ни другая правка его энергопотребления не добавлены. Пропорции и базовые
160 тиков майонезных рецептов сохранены.

Все перечисленные игровые привязки ещё требуют проверки загрузкой реестров,
компиляцией и в игре. Перечень проверок — [ACCEPTANCE.md](ACCEPTANCE.md).

## Сборка

В корне проекта должны находиться:

```
build.gradle.kts
gradlew
gradle/wrapper/gradle-wrapper.jar
ntmjar/ntm-next.jar
```

`layout.projectDirectory.file("ntmjar/ntm-next.jar")` задаёт путь относительно
`build.gradle.kts`, независимо от рабочего каталога оболочки.
Зависимость используется как `compileOnly(files(ntmJar))` и отдельно как
`runtimeOnly(files(ntmJar))` для dev-запусков, без shading.

```sh
./gradlew build
./gradlew runServer
./gradlew -PwithClientDependencies runClient
```

Windows: `gradlew.bat build`. Нужен JDK 25. Wrapper использует Gradle 9.2.1.
Дополнительный флаг клиента разрешает dev-зависимость Crankshaft из Warfactory.
Основной NTM никогда не скачивается и не собирается из исходников этими задачами.

Проверки без загрузки Minecraft/NeoForge:

```sh
python3 tools/check_core.py
python3 tools/check_resources.py
python3 tools/audit_ntm.py ntmjar/ntm-next.jar --output build/ntm-api.json
```

`check_core.py` выполняет серверную модель; производственный симулятор находится
только в test sources и не входит в аддон. `check_resources.py` проверяет JSON,
пропорции, контейнеры, рецепты модулей и ссылки на ресурсы фактического NTM JAR.
Эти проверки не равны игровым тестам.

## Установка после успешной сборки

Поместить отдельные JAR NTM NEXT и `hbmmayo-*.jar` в `mods/` клиента и сервера.
Клиенту дополнительно требуется Crankshaft, как указано в метаданных NTM.
Использовать Java 25 и NeoForge 26.2.0.89. Другие версии не проверены.
Сейчас выполнять установку нечего: успешного JAR аддона ещё нет.

## Игра и конфигурация

Рецепты описаны в [RECIPES.md](RECIPES.md). Модули ставятся в штатном столе
улучшений брони NTM. Энергия берётся с реально надетого нагрудника, не из модуля.

Камера работает в радиусе 3 блоков. HE подводится кабелями NTM или батареей NTM
в первой ячейке простого инвентаря блока. У адаптера вторая ячейка — контейнер
жидкости, третья — результат; доступны также native трубопроводы. Shift+ПКМ
пустой рукой выводит состояние. Адаптер ставится на одной высоте с RBMK колоннами;
область охлаждения — 5×5, как у native Cooler. Менее 50 mB уменьшает мощность
пропорционально заправке; срок работы не обновляется при доливе.

`config/hbmmayo.properties` создаётся из bundled defaults. Все требуемые параметры
доступны в нём, включая `hudX` и `hudY`. Нестабильность и скорость стабилизации
измеряются в процентных пунктах, здоровье — HP, время — тики, энергия — HE.
Перезагрузка файла требует перезапуска игры/сервера. Порог перегрева смазки
по умолчанию 800 в нативных единицах температуры турбины; это настраиваемая
величина, поскольку ТЗ не задаёт точного порога.
